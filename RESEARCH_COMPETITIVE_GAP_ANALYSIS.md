# SpaceWorker — Competitive Gap Analysis

**Date**: 2026-09-04. **Method**: read the actual current codebase (not assumptions) against `PLAN.md` and `TASK_09`–`TASK_12`, then researched five anti-detect/cloud-browser products (GoLogin, AdsPower, Multilogin, Kameleo, GeeLark) and four lead-gen products (Apollo.io, Hunter.io, Clay, PhantomBuster). Mailer competitive research was **not** redone — `PLAN.md` Addendum 2 §4 already covers it in depth; §3 below only adds what that research didn't cover, and confirms the shipped code against it.

## Summary

The "looks empty and scanty" reaction has a concrete, verifiable cause, not a vague one: **the shell (Task 10's OS-style dock) is more finished than the content behind several of its doors.** Two of the three Extract templates ("HR/Recruiting," "Plain Search") are inert stubs a new user can click into and get nothing from; there is no CSV export of leads despite that being explicit original Phase-1 scope; campaigns can only be built from a manually-uploaded CSV, with no path from a completed extraction job into a campaign, even though both features are fully built — so the product's own two automation pillars never actually touch each other; and the landing page (`app/page.tsx`) still reads exactly as it did before Addendum 2's reframing, describing SpaceWorker as "automation tools for lead extraction... and email outreach" with **no mention of the private browser at all**, contradicting the product's own confirmed positioning and probably the first thing any tester actually saw.

The mailer itself (Task 12) is in genuinely good shape — CSV recipients with merge variables, true sender + subject/body rotation, and the test-send-confirm gate are all implemented and match `PLAN.md`'s "must have" tier exactly. The one new finding this pass surfaced is a real one: Gmail/Yahoo/Microsoft's bulk-sender enforcement moved from soft-deferral to **permanent rejection** in late 2025, and the practical spam-complaint ceiling has tightened — this raises the urgency of the "should have" bounce/complaint-handling tier that Addendum 2 already flagged but scoped as lower-priority.

The private-browser and lead-extraction features are where most of the real gap against competitors lives, and — importantly — most of what's missing there is **buildable without violating the no-per-user-VM Phase-1 architecture decision** (`PLAN.md` Addendum 3). A few things genuinely are architecturally gated (real GPU-backed fingerprint diversity, mobile/Android emulation) and are flagged as such rather than recommended.

## 1. Private-browser feature — prioritized gaps

**Current shipped state** (confirmed by reading `components/browser-session-panel.tsx`, `lib/exit-nodes.ts`, `lib/browser-proxy.ts`, `prisma/schema.prisma`'s `BrowserProfile`/`BrowserSession` models, and the Task 7/10 commits): per-user persistent Chrome profile directories reused across sessions; interactive sessions streamed via Neko/Docker into a dashboard iframe (`/browser/{sessionId}/`); free self-hosted exit-node routing (US/UK, env-gated) or a per-profile BYO proxy (host/port/scheme/user/pass, AES-256-GCM encrypted, test-connect before save); a live "what's my IP" checker that actually round-trips through the active proxy (`lib/browser-proxy.ts`'s `checkIpThroughProxy`, not a cached value); an in-session location switcher; admin-side force-release/kill routes. This is a real, working implementation of Addendum 3's confirmed Phase 1 scope — not a stub.

| Priority | Gap | Why it matters / competitor precedent | Feasibility note |
|---|---|---|---|
| **High** | No local automation/CDP hook into a running profile | GoLogin's and AdsPower's local API/LocalAPI (and AdsPower's new MCP server) let a script (Selenium/Puppeteer/Playwright, or now an AI agent) drive an already-open, already-fingerprinted profile. This is the single most-cited "serious tool" feature in the research and it's a natural bridge between SpaceWorker's own automation pillar (extraction) and its browser pillar — closing the "three unrelated features" gap from inside the architecture, not just the UI. | **Feasible now.** The Neko container's Chromium already exposes a CDP endpoint internally; this is an authenticated proxy/route to it, not new infrastructure. No VM needed. |
| **High** | Fingerprint masking is undisclosed as a limitation, and the interactive session likely reports a software renderer | The whole anti-detect category (GoLogin's Orbita fork, Multilogin's Mimic/Stealthfox engines, Kameleo) exists to control canvas/WebGL/font/timezone/hardware-concurrency fingerprints per profile. SpaceWorker streams a real, unmodified Chromium in a headless-container-with-virtual-display (Xvfb) setup — which is architecturally the same "no real GPU" situation Addendum 3 already flagged for the deferred microVM plan (`llvmpipe`/`SwiftShader` as the WebGL renderer, a top bot-detection signal), just not yet called out for the **already-shipped** interactive browser. Addendum 3 sets a precedent of honesty here ("never market as an antidetect-browser replacement") — that same disclosure needs to reach the *current* private-browser UI, not just future sales copy, since a real customer is using it today. | **Partially feasible now, fully feasible later.** Disclosing this plainly in the UI costs nothing. Actual GPU passthrough for real WebGL rendering needs real hardware — correctly gated behind the Phase 2 bare-metal decision, not a Phase 1 task. |
| **Medium** | No profile grouping/tags/bulk actions | AdsPower and Multilogin both organize profiles into groups (by campaign/client/platform) with bulk create/share/proxy-assign. SpaceWorker's Browser Profiles page (`app/dashboard/browser-profiles/page.tsx`) is a flat list. Not a problem at today's low profile-count-per-user, but will feel thin as soon as a user has more than a handful of profiles. | Feasible — pure data-model + UI work (a `tag`/`group` string column, filter UI). Not urgent. |
| **Medium** | No session history/duration record visible to the user | Every competitor surfaces "when did I last use this profile / for how long" somewhere. `BrowserSession` already has `startedAt`/`endedAt` in the schema — this is stored but apparently not rendered as a history view once a session stops (only current sessions are shown in the panel). | Feasible, small — a read-only list under Browser Profiles or Private Browser. |
| **Low** | No shared/managed extension store | AdsPower manages Chrome/Firefox extensions centrally and pushes them into profiles. Since Neko streams a real Chrome UI, a user *can* already install extensions manually inside a session — this gap is about platform-side convenience, not capability. | Feasible later; low value at current scale. |
| **Low (deliberately out of scope)** | No team/multi-seat profile sharing, no mobile/Android emulation (GeeLark/Kameleo's cloud-phone angle) | Both are real competitor differentiators, but `PLAN.md`'s own Phase 1 scope explicitly defers "team/multi-seat accounts," and mobile emulation is a different product category entirely (GeeLark's own pivot to a *unified* browser+cloud-phone platform in 2026 shows even they treat it as a second, separate infrastructure layer). Not recommended for this stage. | Correctly out of scope — no action needed. |

## 2. Lead-extraction feature — prioritized gaps

**Current shipped state** (confirmed via `app/dashboard/extract/page.tsx`, `app/api/jobs/route.ts`, and `TASK_11_LEAD_EXTRACTOR_TEMPLATES.md`): a three-template picker (Lead Search / HR-Recruiting / Plain Search); Lead Search is fully wired end-to-end with a real multi-term "Find" list (chips, not a single string), engine choice (DuckDuckGo/Google), and lane (quick/deep); HR and Plain Search render their own distinct fields but their Search button just returns an inline "coming soon" message — by design, per Addendum 5's explicit instruction not to fake an engine that doesn't exist yet.

| Priority | Gap | Why it matters | Feasibility note |
|---|---|---|---|
| **High** | **No CSV export of leads** | This was explicit original Phase 1 scope in `PLAN.md` line 91 ("lead export (CSV)") and is not implemented — grep across the whole app/lib tree finds zero export code path for `Lead` rows (the only CSV code in the repo is the Mailer's *recipient upload* parser). Every competitor researched (Apollo, Hunter, PhantomBuster) treats "get your data out" as table stakes; its absence here is a regression against the product's own stated scope, not just a competitive gap. | Small, self-contained — a `GET /api/jobs/[id]/export.csv` route and a button. Should be the fastest fix on this list. |
| **High** | **No path from a completed extraction job into a campaign** | `EmailCampaign.searchJobId` exists in the schema and `POST /api/campaigns` already accepts it, but the Campaigns UI (`app/dashboard/campaigns/page.tsx`) only offers a manual CSV upload — there is no "build a campaign from Job X's leads" flow. This is precisely the gap Addendum 4 calls the hard-dependency blocker for the Automation tab/campaign-template system, and per this session's reading, **both of that addendum's stated blocking conditions now look satisfied**: Task 2 (extraction worker) is deployed and is what Task 11's Lead Search template runs against today, and Task 9's mailbox/campaign verification report concluded "solid enough for the campaign-automation work to build on." Addendum 4's own sequencing note ("fix Task 2, verify Task 4, then scope this") appears cleared — this can likely move from "blocked" to "ready to scope" now. | This is the single highest-leverage cohesion fix on the whole list — it is what turns "two tools that happen to share a login" into one product. |
| **Medium** | No lead verification/enrichment before use | `PLAN.md` already flags `hr-recruitment-extractor`'s `email_enricher.py` (MX lookup, RCPT-TO verification without sending) as available-to-harvest and explicitly deferred past Phase 1. Hunter.io and Clay's entire value proposition is verified-email accuracy; re-surfacing this here because of a new cross-pillar reason: the Gmail/Yahoo enforcement tightening found in this pass (§3 below) makes sending to unverified/dead addresses materially riskier to a customer's sender reputation than it was when Addendum 2 was written — this is no longer just a "nicer leads" feature, it's a mailer-reputation-protection feature. | Real backend work, correctly still a "later" item — but the priority argument for it has gotten stronger, not weaker, since Addendum 2. |
| **Medium** | No lead management (dedupe across jobs, status/tags, notes) | `Lead` has a `@@unique([searchJobId, sourceUrl])` constraint — dedupe is per-job, not per-user, so the same business found by two different searches shows up twice with no cross-job awareness. Apollo/Clay-style tools treat "which leads have I already contacted" as core. | Feasible, moderate scope — a per-user uniqueness pass and a `status` field. |
| **Low, but visible** | Two of three template tabs are non-functional today | Correctly built as explicit "coming soon" rather than a silent no-op (good judgment call by Task 11's implementation) — but this is very likely a direct contributor to "looks empty": a new user's first exploration of the Extract tab has a 2-in-3 chance of clicking a template that does nothing. Given Addendum 5 frames "Plain Search" as the simplest to build (a general web search, no fixed extraction shape), it may be the cheapest way to reduce that specific feeling of emptiness without waiting on the harder HR/Recruiting backend. | Worth a small, focused push on Plain Search specifically, not both — HR/Recruiting has its own separate, genuinely different backend problem per Addendum 5 and shouldn't be rushed to match. |
| **Low (architecturally distant, not gated)** | No LinkedIn/Sales-Navigator-style logged-in scraping (PhantomBuster's core use case) | PhantomBuster's Sales Navigator scraper works specifically because it drives a *logged-in* session. SpaceWorker already has exactly the infrastructure this needs — the per-user persistent browser profile (Task 6/7) — so this is a genuine future synergy between the private-browser pillar and the extraction pillar, not a new architecture. Flagging as a direction, not a near-term ask — it's a new "template" (per Addendum 5's own template-system framing) and real new backend work, same caveat Addendum 5 already applies to HR/Recruiting. | Not gated by the no-VM decision at all — just not scoped yet. |

## 3. Mailer — confirmation and new findings only (not a repeat of Addendum 2 §4)

**Verified against the actual shipped code** (`prisma/schema.prisma`, `app/api/campaigns/route.ts`, `lib/csv.ts`, `lib/imap.ts`, `lib/deliverability.ts`, `lib/seed-mailbox.ts`, `lib/mailer-send.ts`, and the campaign UI): Task 12's full "must have" tier from Addendum 2 §4 is implemented, not partially — CSV recipient upload with per-recipient merge variables (`lib/csv.ts`'s `parseRecipientsCsv`), a real `CampaignVariant` model with round-robin subject+body rotation, true in-run sender rotation across a `mailboxIds[]` set (assigned per-item at creation via `i % mailboxIds.length`), and a `pending_test_confirm` gate that sends a real token-stamped test message and polls a platform-owned `SeedMailbox` over IMAP (`imapflow`) before unlocking the real send. The "should have"/"nice to have" tiers (checkpoint deliverability monitoring, bounce/complaint handling, spintax, open-rate A/B, warmup) are confirmed **absent**, matching Addendum 2's own deferral — nothing here contradicts the plan.

**Spot-check on staleness**: Addendum 2 §4's sources (MailReach, SmartReach, Instantly/Smartlead blogs on spintax/A-B testing/seed lists) describe mechanics — rotation, spintax, seed-list testing — that don't have a "went stale" failure mode; re-checked current 2026 sources on the same mechanics and found no material change to how those techniques work. What **has** changed, and wasn't in Addendum 2's research:

- **New finding — Gmail/Yahoo/Microsoft enforcement got harder, not just stricter.** As of November 2025, Gmail moved from soft-deferring non-compliant bulk mail to **permanently rejecting** it, and the practical spam-complaint ceiling that keeps a sender out of trouble has tightened to roughly 0.10% (compliant senders now average ~89% inbox placement; non-compliant senders see 22–34% landing in spam — a 3–7x penalty). This doesn't change anything about *what* Addendum 2's priority table recommends, but it changes the cost of skipping the "should have" bounce/complaint-handling tier: a mailbox that racks up hard bounces or complaints today risks the sending domain being rejected outright, not just spam-foldered. **Recommendation: consider pulling bounce/complaint handling forward from "should have, Phase 1.5" to "do shortly after must-have ships," given the downside changed from degraded delivery to a hard wall.**
- **New finding, cross-referenced with §2 above**: the lead-extraction gap on email verification (§2, "Medium") and this mailer finding are the same underlying risk from two different entry points — an unverified/dead lead is exactly the kind of address that generates the hard bounces the tightened Gmail policy now punishes harder. This wasn't flagged as a connected pair anywhere in the existing plan; worth treating as one prioritization decision rather than two separate backlog items.
- **New, small implementation-detail finding (not in Addendum 2/Task 12, found by reading the actual `POST /api/campaigns` code)**: mailbox rotation is assigned **once, at campaign-creation time** (`mailboxIds[i % mailboxIds.length]` over the recipient array), not re-evaluated at drain/send time. Task 12's own spec left this as an open choice ("pick one and note it") without discussing the consequence: if mailbox A hits its `dailyLimit` mid-campaign, the items already assigned to A simply wait for tomorrow rather than being redistributed to a mailbox that still has headroom — so a campaign with an uneven per-mailbox daily-cap mix can spread over more days than the "N mailboxes rotating" framing implies, and the rotation ceases to be even under real daily-cap pressure. Not a correctness bug (nothing double-sends or drops), but worth a conscious decision: keep it (simpler, predictable) or move assignment to drain-time (evener under caps, more complex). Flagging since it wasn't discussed anywhere in the existing research or task specs.

Nothing else in Addendum 2 §4/§5, Addendum 6, or Task 12 needs revision — the "must have" tier's own priority ordering and reasoning still hold.

## 4. Overall product-cohesion gaps

The core finding: **the shell now looks like one product (Task 10's dock/desktop redesign is a real, working, visually consistent OS-style shell across Overview/Extract/Mailboxes/Campaigns/Browser Profiles/Private Browser/Settings) but the content behind it still behaves like three separate tools that happen to share a login**, for three concrete, fixable reasons already surfaced above:

1. **No Automation tab exists yet.** Addendum 4 already designed this — a cross-cutting tab, extensible by sub-tab, whose first instance is the "mass ads" campaign-template flow tying lead volume + segment + sender rotation + deliverability gate into one guided flow. This is the single feature that would make "extract → filter → send" visibly one workflow instead of three separate destinations a user has to manually stitch together. Per §2 above, its stated blocking conditions (Task 2 solid, Task 4 verified) both look satisfied now — this is likely unblocked, not just planned.
2. **The landing page (`app/page.tsx`) still contradicts the product's own confirmed positioning.** It reads "Automation tools for lead extraction, filtering, and email outreach" — the pre-Addendum-2 framing — and doesn't mention the private browser at all, despite Addendum 2 §1 explicitly correcting this to "a private browser workspace, with automation as one capability riding alongside it." This is very likely close to verbatim what the product owner saw when testing live and calling it "scanty" — the front door undersells even what's already built.
3. **Extraction and mailer don't hand off to each other** (§2's "High" finding) — each is complete on its own but the product has no built path connecting them, which is the functional definition of "features bolted together" rather than "one tool."

For context on how the researched competitors solve this same problem: Clay and Apollo both make the *workflow* (not the individual data source) the primary UI object — a user builds one pipeline that calls multiple underlying capabilities, rather than navigating between separate screens for each capability. SpaceWorker's own Addendum 4 design (Automation tab, template system) is directionally the same idea, already designed, just not yet built.

## 5. Explicitly infeasible given Phase-1 architecture (flagged, not recommended)

Per `PLAN.md` Addendum 3's locked decision (no per-user VMs at this stage, shared VPS, no bare-metal spend yet):

- **Real GPU-backed fingerprint diversity** (unique WebGL/hardware fingerprints per profile that would pass rigorous bot-detection) — needs either real GPU passthrough or the kind of per-VM isolation Phase 2's bare-metal plan describes. Not buildable on the current shared VPS regardless of engineering effort; correctly deferred, and — per §1 above — should be actively disclosed in-product now, not just planned for later sales copy.
- **A residential/mobile proxy pool of SpaceWorker's own** (what "dedicated IP" means in GoLogin/Multilogin/AdsPower) — Addendum 3 already confirmed this is deferred in favor of free self-hosted exit nodes + BYO, for cost reasons, not technical ones; nothing in this research changes that call.
- **Mobile/Android device emulation** (GeeLark, Kameleo) — a different infrastructure category (Android VM/emulator farm), not an extension of the current Neko/Chromium approach; correctly out of scope for this stage.
- **Unlimited concurrent interactive sessions** — Addendum 3's 2–3 session cap is a deliberate, stated Phase 1 ceiling tied to current VPS resources, not a gap to close via engineering; it needs bigger hardware, which is explicitly a Phase 2 decision.

None of the "High" or "Medium" priority items in §1/§2/§4 above require violating this architecture — they were chosen specifically because they don't.
