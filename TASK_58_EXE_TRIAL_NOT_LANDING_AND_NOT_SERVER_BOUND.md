# Task 58 — EXE trial not showing in admin, and not actually server-bound (resettable)

**Status: ready to build. Owner-requested 2026-09-21**, found live: "i just loaded the spaceworker, and it should have shown in the admin under active trials... can you investigate why i cant see it, and if the trial license is actually binding, so anonymous users dont just use it on notice."

Two separate questions, two separate findings.

## Part A — why didn't this specific trial show in admin

Server-side pipe is sound (Cline's own synthetic ping landed a row; the admin query in `app/api/admin/exe-trials/route.ts` filters/joins correctly; `HOSTED_APP_URL` is hardcoded correctly in `lib/exe-runtime.ts`; the product id resolves fine). The gap is between the real installed EXE and the server.

**Strongest lead — check this first, it's fast**: `trial-ping` (`app/api/exe-license/status/route.ts`'s `pingTrialStatus`, and `app/api/exe-license/trial-ping/route.ts`) was only added TODAY, commit `7f540d1` (2026-09-20 15:27 +0100 = 14:27 UTC). `gh run list -R softdeployautomation-sketch/spaceworker --workflow="Build EXE"` shows builds at 11:44, 12:08, 12:17, 13:08, and 21:49 UTC on 2026-09-20 — everything **before** 14:27 UTC does not contain the trial-ping feature at all; only the 21:49 UTC build (`e4c1ff9`) does. If the EXE the owner just tested was installed from any of the earlier same-day builds, it simply has no trial-ping code to run — no bug to chase, just a stale install.

1. Confirm which build is actually installed on the machine that was just tested (ask the owner, or check the installer's build timestamp/version if the app surfaces one).
2. If it predates `7f540d1`: trigger a fresh `gh workflow run "Build EXE"`, reinstall per `HOW_WE_MOVE_FAST.md` §5, and retest. This alone may fully resolve Part A.
3. If the installed build IS current and it *still* doesn't land: the fire-and-forget ping in `pingTrialStatus()` swallows every error silently (`.catch(() => {})`, line ~39) — there is currently no way to know if the real EXE's outbound HTTPS to `https://spaceworker.instaweb.top` succeeded, timed out, or hit a DNS/firewall issue on that specific Windows machine. Add a temporary non-silent path (e.g. write the fetch's resolved status/error to the EXE's own local log file, not just swallow it) to actually observe what happens on a real retest, rather than guessing further.

## Part B — the trial is not actually server-enforced, AND it's fully anonymous (owner wants both fixed — this replaces the silent-trial model)

**Owner's explicit direction (2026-09-21), supersedes the "silent trial" design entirely**: *"the flow should take users email from the start, not just allow users to just use the app, so that email binds with the free for 24hrs until the premium comes in if they pay."* No more anonymous first launch. Email capture becomes a required, one-time step BEFORE the trial (or the app) is usable at all — and that email becomes a real binding key server-side, not just a display label.

### Current state (what's being replaced)

`components/license-gate.tsx` currently has exactly two rendered states: `loading` and `ok` (trial or licensed) or `expired`. On mount it silently `POST`s `/api/exe-license/status` with **no user interaction at all** — see its own file-top comment: *"First launch / during the silent 24h trial -> NO gate. The app opens straight into the dashboard and the local trial timer starts behind it."* `lib/license-state.ts`'s `startTrialIfNeeded()` likewise starts the clock the instant the local file is missing, no email, no prompt, nothing. This is what let the earlier "anonymous users can just reset by deleting a file" gap exist in the first place, compounded by there being no email on file to even identify who's using it.

`ExeTrialSession` (`prisma/schema.prisma` line 523) currently has no `email` column at all — only `machineId`, `product`, `machineLabel`, `startedAt`, `lastSeenAt`.

### The new flow

1. **`prisma/schema.prisma`**: add `ExeTrialSession.email String` (required — a trial can no longer exist without one) and a migration. Decide alongside this whether the uniqueness key stays `@@unique([machineId, product])` or becomes `@@unique([machineId, product, email])` — **keep it `[machineId, product]`**, not a 3-way key: the whole point of Part B's hardware-binding fix below is one trial per physical machine, and a 3-way unique key would let someone reset the clock just by submitting a different email in the same 24h from the same machine, undermining it. `email` should be a plain stored field the FIRST successful start writes and never changes afterward (same "startedAt never resets" discipline the upsert already uses for the timestamp).

2. **`components/license-gate.tsx`**: add a new `Status` mode, e.g. `{ mode: "needsEmail" }`. On mount, instead of unconditionally POSTing `/api/exe-license/status`, first check local state: if there's no activation AND no local trial start recorded yet, render an email-capture form (a small, single-field card — reuse `Card`/`Badge` styling already imported here, roughly matching the existing "Trial expired" card's shape further down this same file) BEFORE calling status. Only after the user submits an email does the app call the (now email-carrying) trial-start endpoint and proceed to `ok`. A returning user who already has a local trial started (or an activation) skips straight past this exactly as today — this is a ONE-TIME first-run step, not a nag on every launch.

3. **Server side** — extend `app/api/exe-license/trial-ping/route.ts` (or add a sibling `trial-start` endpoint if keeping ping's fire-and-forget shape is cleaner — Cline's call, but don't have two competing sources of truth for `startedAt`) to accept `email` in its body (`z.string().email()`), and make it the ONE place `ExeTrialSession` rows are created — i.e. this call becomes **required and awaited** on first run (not fire-and-forget like today), returning the authoritative `startedAt` in its response. This same call also closes the Part-B hardware-binding gap from the original draft of this task: `getMachineId()` (`lib/machine-id.ts`) already derives a stable hardware fingerprint that survives reinstalls, and the upsert already never resets `startedAt` on repeat calls — so a returning machine (even with its local state file deleted) gets its TRUE original `startedAt` back from the server on this same required call, not a fresh 24h.

4. **`app/api/exe-license/status/route.ts`**: the local-only trial path (`startTrialIfNeeded()`) is no longer the primary source of truth for a NEW trial — a trial cannot start without the email step (#2) having already called the server successfully. `status` itself can stay reading the local file for the common case (fast, offline-tolerant after the initial handshake), but should reconcile against the server's `startedAt` the same way the original Part B draft specified — the earlier of local/server wins, so the file alone can never move the clock forward.

5. **Admin visibility**: `app/api/admin/exe-trials/route.ts`'s response and whatever renders it in `/admin101` should now show the captured `email` alongside `machineLabel` — this was explicitly part of the ask ("a subtab showing every free user's device," now with a real identity attached instead of just a machine label).

6. **Nice-to-have, not required for this pass**: once the user later buys/activates a real license, prefill the email they already gave at trial-start into `components/license-activation-form.tsx`'s email field (read from the local state file) — saves them re-typing it, and ties the eventual paid activation back to the same person who trialed. Skip if it adds meaningful scope; the required pieces are 1-5 above.

### What NOT to build here

Don't build a global "one trial per email across every machine" cap in this pass — the owner's ask was specifically about binding the trial to an email *and* it staying tied to the hardware it started on, not a cross-device account system. `[machineId, product]` stays the unique key per point 1. If the owner later wants a cross-device cap, that's a separate, bigger task (would need real account/auth infrastructure for the EXE, which doesn't exist today).

**Verification expected**: fresh install, launch → email prompt appears before any dashboard access (confirm the app is NOT usable without it — this is the core of the ask, "not just allow users to just use the app"); submit a valid email → dashboard opens, trial running, `ExeTrialSession` row has the email; admin "Active trials" shows the email; delete the local state file, relaunch → email prompt does NOT reappear if the server round-trip in `status` succeeds (machine already known) and remaining trial time matches the ORIGINAL start, not a fresh 24h; confirm a genuinely new machine with no prior server record gets a normal fresh prompt+trial; confirm existing activated/licensed users see no change at all (this only touches the pre-activation trial path).
