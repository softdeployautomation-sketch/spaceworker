# Task 36 — Fix mailbox starvation in the batch gate, and switch_subject's silent no-op / missing re-verification

**Status: URGENT — same file as Task 33 (`app/api/internal/mail-queue-drain/route.ts`, `app/api/campaigns/[id]/deliverability-decision/route.ts`). Fix this as part of wrapping up Task 33 in these files, ahead of moving to Task 34/35.** Two real bugs confirmed live on a real 150-recipient, 2-mailbox campaign on 2026-09-13, via direct production DB inspection — not speculation.

## 1. Mailbox starvation: one mailbox can monopolize an entire campaign's per-tick batch quota

**Confirmed via direct query** on the live DB: campaign `mailboxIds` correctly contained both mailboxes, `rotateEvery: 10` correctly assigned queue items 80/70 across them at creation time (matching the rotation math exactly — 8 alternating blocks of 10 to mailbox A, 7 to mailbox B). But after 66 real sends, **all 66 had gone through mailbox A; mailbox B had sent zero**, despite having 70 of its own items sitting queued the whole time.

**Root cause**, in `app/api/internal/mail-queue-drain/route.ts`: the outer loop is `for (const mailbox of mailboxes)`, and the batch-gate admission counter (`dispatchedThisTick`, capped at the campaign's `batchSize`) is shared across the WHOLE campaign but consumed per-mailbox in loop order. Whichever mailbox is iterated first for a given campaign greedily admits up to the entire `batchSize` from its own queue if it has enough items — mailbox A had 80 queued (more than `batchSize: 50`), so it filled the whole quota by itself, every single tick, leaving mailbox B's turn (later in the same loop) with `dispatchedThisTick` already maxed and nothing left to admit. This continues until mailbox A's own remaining queue drops below `batchSize`, at which point mailbox B finally gets a look-in — for this campaign, that took 70+ sends and roughly that many minutes (each tick is a long-running, fully sequential per-item send with the existing 5-45s jitter, so a tick that admits close to the full batch can itself take many minutes).

**This silently violates the user's own configured rotation** — `rotateEvery: 10` promises alternation every 10 recipients; what actually happened on the wire was 66 recipients in a row through one mailbox, none through the other, which is exactly the kind of unnatural, bursty pattern that hurts sender reputation (the same category of risk Task 35's pacing research flagged) — the bug doesn't just look wrong, it actively undermines the reason rotation exists.

**Fix**: give each of a campaign's mailboxes a FAIR per-tick share of the batch quota instead of first-come-greedy — e.g. `perMailboxCap = Math.ceil(campaignBatchSize / campaign.mailboxIds.length)`, so no single mailbox can consume more than its proportional share in one tick even if it has plenty of items queued. (An alternative, more thorough fix — process a campaign's admissible items in original rotation/recipient order across all its mailboxes rather than mailbox-outer-loop order — would also work and more precisely preserves wall-clock alternation, but the per-mailbox sub-cap is the smaller, lower-risk change; use your judgment on which reads cleaner in the actual loop structure once Task 33's changes are in place.) Either way, the goal is: within any handful of consecutive ticks, a 2-mailbox campaign with `rotateEvery: 10` should visibly alternate on the wire, not front-load one mailbox entirely.

## 2. `switch_subject` needs re-verification before resuming, and must not be a silent no-op for legacy campaigns

Confirmed by re-reading the currently-deployed `deliverability-decision` route: from a batch pause, `switch_subject` rotates `subjects` (when the campaign is decoupled) and immediately sets `status: "sending"` — **with no fresh test-send of the new content**. This is inconsistent with the campaign's OWN initial gate, which required an explicit test-send + human confirm before ever reaching `"sending"` the first time; resuming after a mid-campaign spam-hit with zero re-verification undermines the exact protection the batch gate exists to provide.

**Worse for a legacy (non-decoupled) campaign** — like the one this was tested on (`"No variants on this legacy campaign"`, empty `subjects`/`bodies`): the rotation code path (`Array.isArray(campaign.subjects) && campaign.subjects.length > 1`) is simply false, so `rotatedSubjects` is `undefined` and the update does NOTHING to the content — the campaign resumes sending with the EXACT SAME subject that just failed a deliverability check, silently. The user experiences this as "I asked it to try something different, and it just went ahead" — because nothing about the message actually changed.

**Fix, two parts**:
- For a legacy campaign, `switch_subject` should NOT be offered as-is (it has nothing to rotate to) — either disable/hide that specific button for legacy campaigns and point the user at Task 32's "Manually edit and test" path instead (which already handles legacy campaigns correctly, upgrading them into the decoupled model on promotion), or — if there's more than one `CampaignVariant` row for this campaign — rotate through those instead. Check which is simpler given Task 33's other changes to this route; either is acceptable as long as clicking the button never silently does nothing.
- For ANY campaign (decoupled or not), `switch_subject` resuming from a batch pause should run a real test-send of the NEW content before flipping back to `"sending"` — mirroring the initial gate's own discipline. This likely means `switch_subject` should transition the campaign into the SAME "awaiting a fresh test" shape the initial gate uses (or directly invoke the equivalent of a test-send server-side) rather than assuming rotation alone is enough proof. Coordinate this with whatever Task 33's isolation-diagnostics work already does in this exact area — there may already be a natural integration point once probes have their own re-verification step built.
