## What's wrong today (confirmed by reading the live code, not assumed)

The current extractor (`worker/automation.py`) does a **single page of Google/DuckDuckGo search results**, then for each result either fetches the page via plain `requests.get()` (no JS rendering) or falls back to regex-extracting an email/phone/name from the search **snippet text** if the page fetch fails or the page is empty. There is:
- No PDF handling of any kind — PDF search results are just treated as another page URL and `requests.get()`'d as HTML, which does nothing useful against PDF bytes.
- No pagination — only the first page of results per query is ever visited (`search_phase()` → `google_search()`/`duckduckgo_search_http()`, capped at `max_results` results total, single call).
- No run-duration cap, no pause, no resume — a job runs to completion or is hard-cancelled (`DELETE /jobs/{id}` in `worker/api.py`), which **discards everything found so far** (see "Leads are not persisted incrementally" below).

This produces exactly the kind of junk the user flagged live: leads like a phone number and a name pulled from an unrelated Wikipedia bio's snippet text, because the real page had nothing extractable and the code fell back to guessing from search-result metadata instead of real page/PDF content.

## The target behavior (user's own spec, verbatim intent)

For each search query: go to Google, and on the results page, click into **every PDF result** and extract email addresses from the PDF's actual text content; for every non-PDF result, extract emails from the real page content (this part already exists via `extract_lead_page()` — reuse it, don't rewrite it, see below). Then click to the next page of Google results and repeat, up to a configurable number of pages (10–20, user-configurable per query before it moves to the next term). If total leads found across all queries falls short of the requested minimum, keep adding related query variants (this partially already exists — see "Reuse, don't rebuild" below). The whole job should respect a maximum run duration (e.g. 30 minutes) and be pausable — pausing means finishing the query currently in progress, then stopping there; resuming continues from the next not-yet-processed query rather than starting over, and whatever leads were already found before the pause must not be lost.

## Part 1 — Real crawler: Google pagination + PDF click-through

**File: `worker/automation.py`**

1. `google_search()` (currently returns one page of results) needs to become page-aware — either change its signature to accept a page/start-offset and call it in a loop, or add a new function `google_search_paginated(query, pages_per_query, job_dir)` that internally drives Playwright through Google's "Next" pagination (Google's results URL takes a `start=` query param in multiples of 10 — confirm this is still true by inspecting a real live Google results page during implementation rather than assuming, since Google changes markup/params without notice). Cap hard at `pages_per_query` (see Part 3 for where this comes from) regardless of what the UI sends, same defensive-clamping pattern already used for `max_results` in `search_phase()`.
2. For each result URL on each page, before calling the existing `extract_lead_page(result)`, detect whether it's a PDF — cheapest reliable check is the URL ending in `.pdf` (case-insensitive) OR a HEAD/GET response `Content-Type: application/pdf` (prefer checking the response header over trusting the URL extension, since some PDFs are served without a `.pdf` URL). Add a new function `extract_lead_pdf(result: SearchResult) -> list[dict]` that downloads the PDF bytes and extracts text from it, then calls the **same** `_build_leads(result, emails, phones, contact_names)` used by `extract_lead_page()` (same fallback ordering: emails first, then phone/name-only, then nothing).
3. Add `pypdf` to `worker/requirements.txt` (pin an exact version, e.g. `pypdf==4.2.0` — check PyPI for the current stable release at implementation time) for PDF text extraction — it's pure-Python, no system dependency, unlike `pdfplumber`/`PyMuPDF`. Extract text via `PdfReader(BytesIO(pdf_bytes)).pages[i].extract_text()` across all pages, concatenate, then run through the existing `_extract_emails`/`_extract_phones`/`_extract_contact_names` functions exactly as `extract_lead_page()` does for HTML text.
4. A PDF that fails to parse (corrupt, encrypted, scanned-image-only with no text layer) should be skipped with 0 leads, not crash the job — wrap the extraction in try/except mirroring `extract_lead_page()`'s existing try/except around `requests.get()`.
5. `_search_and_extract()` (the function that currently does one pass of search+extract per round) needs to loop over pages-per-query and branch PDF vs. non-PDF per result, rather than its current single flat pass. Read this function in full before changing it — it's the shared core both the initial pass and the expansion rounds call today, and that sharing should be preserved.

## Part 2 — Persisted, resumable job state (this is the load-bearing structural change)

**Confirmed by reading `app/api/internal/dispatch/route.ts` lines 145-204**: leads are currently only written to Postgres **once, at job completion** (`if (data.status === "done")`), pulled entirely from the worker's in-memory `JobState.leads` list in `worker/api.py`. A hard-cancelled job (`DELETE /jobs/{id}`) discards `state.leads` and deletes the job's temp directory — **nothing found before a cancel is ever saved.** This is why pause has to change more than just "stop looping": it needs the leads found so far to actually reach the `Lead` table, and it needs enough state recorded to resume from the right spot.

**Design** (implement this shape; if you find a cleaner way to get the same guarantees, fine — but the constraints below are not negotiable: no data loss on pause, no restarting from query 1 on resume):

1. **File: `worker/api.py`** — `get_job()` already returns `state.leads` regardless of status (nothing to change there). Add a new way to signal "pause" to a running job: a new endpoint `POST /jobs/{job_id}/pause` that sets a flag the running `run_automation()` task checks between queries (an `asyncio.Event` or a plain flag on `JobState`, checked at the top of each query's iteration in `worker/automation.py`'s outer loop — NOT mid-query, per the user's explicit "pause means it stops at that certain query"). When the flag is observed, `run_automation()` should return normally (not raise/cancel) with whatever leads were accumulated so far, PLUS a `resumeState` payload (see below) — `worker/api.py`'s `run_job()` should set `state.status = "paused"` (a new status value, not `"done"`/`"failed"`) when `run_automation()` signals it stopped early via pause, and must **not** delete `job_dir`/discard `state.leads` in that case the way a hard-cancel does today (read the `finally:` block in `run_job()` carefully — the `shutil.rmtree` and semaphore release still need to happen, but the leads must already have been read by the dispatcher first, or copied out before cleanup — sequence this carefully, don't lose the leads to a race with the prune/cleanup logic).
2. **`resumeState` shape** — needs enough to continue without restarting: which base/expanded query terms have already been fully processed, the index of the next query to process, and (per the "how it stores the extracted and the continue" instruction) how many Google result-pages were completed for a query that was only partially done when paused, if pausing can happen mid-query-list-but-between-pages rather than strictly between queries — resolve this ambiguity by making "pause" always land on a query boundary (never mid-query), which is what the user actually described ("pause means it stops at that certain query") — simpler and matches the spec exactly, don't build finer-grained resume than asked for.
3. **File: `prisma/schema.prisma`** — `SearchJob.status` needs to allow a new value `"paused"` (it's a plain string column already, no enum to migrate — just start writing the new value). Add `SearchJob.resumeState Json?` (nullable, additive — write a migration under `prisma/migrations/<timestamp>_add_search_job_resume_state/migration.sql` following the exact style of the existing `prisma/migrations/20260905000000_add_browser_session_hidden/migration.sql` — plain `ALTER TABLE "SearchJob" ADD COLUMN "resumeState" JSONB;`).
4. **File: `app/api/internal/dispatch/route.ts`** — Phase B's poll loop (lines ~153-204) needs a third branch alongside the existing `data.status === "done"` / `data.status === "failed"` checks: `data.status === "paused"` should persist `data.leads` into the `Lead` table using the **exact same** `prisma.lead.createMany(...)` block already used for `"done"` (don't duplicate the mapping logic differently — extract it to a small local helper if that avoids copy-pasting the same object-mapping twice), then `safeUpdateSearchJob(job.id, { status: "paused", resumeState: data.resumeState ?? null })` instead of the `"done"` update. Worker's `GET /jobs/{id}` response (`worker/api.py`'s `get_job()`) needs `resumeState` added to its returned dict when present on `JobState`.
5. **File: `app/api/jobs/[id]/route.ts`** — add a `PATCH` handler (or extend the existing route — check what HTTP methods already exist in this file before adding, don't collide with the existing `DELETE`) accepting `{ action: "pause" | "resume" }`. `pause`: ownership check, must be `status === "running"` with a `workerJobId`, calls `POST {workerBase}/jobs/{workerJobId}/pause` (new worker endpoint from step 1), then optimistically nothing else — let the dispatcher's next poll tick pick up the resulting `"paused"` status and leads (don't try to synchronously wait for the worker to actually finish its current query here, that could take a while — this route just requests the pause). `resume`: ownership check, must be `status === "paused"` with a non-null `resumeState`, mints a **new** `workerJobId` (call `POST {workerBase}/jobs` again, same as the dispatcher's Phase A claim logic in `app/api/internal/dispatch/route.ts` — read that section for the exact request shape) with `params` merged to include the stored `resumeState` so `run_automation()` knows to skip already-completed queries, then sets `SearchJob.status = "running"` with the new `workerJobId` and clears `resumeState` back to null (it'll be repopulated if paused again).
